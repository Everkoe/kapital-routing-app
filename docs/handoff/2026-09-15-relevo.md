## 2. Qué es la aplicación

Plataforma B2B de gestión de flota y ruteo logístico para Perú (SOAT, CITV, TUC/ATU,
licencia MTC). Cuatro roles, cuatro portales, una sola SPA:

| Rol | Componente | Función |
|---|---|---|
| Administrador | `FlotaView.jsx`, `AdminDashboard.jsx` | Flota, aprobación de conductores, revisión documental |
| Gerente / Programador de rutas | `GerentePortal.jsx` | Planifica y publica rutas. **Congelado por decisión de fase** |
| Cliente | `ClientPortal.jsx` | Consulta rutas de su empresa |
| Conductor | `DriverPortal.jsx` | Onboarding, documentos, sus rutas |

Volumen real: 112 usuarios (108 conductores), 108 unidades, 193 rutas, **2.645 pasajeros**,
86 notificaciones. El 74,2 % de los pasajeros está en rutas `SIN ASIGNAR` — anomalía
registrada a propósito en `docs/phase-0/data-inventory.md`; no se corrige todavía.

**Stack.** Vite + React 19 estático en Vercel. Backend FastAPI en **un solo archivo**,
`frontend/api/index.py` (~4.620 líneas, 45 endpoints), como función serverless. Sin SDK de
Supabase ni de Gemini: REST puro con `httpx`, decisión deliberada por el límite de bundle de
Vercel. WebSockets nativos. Verificación de SOAT/CITV/licencia contra una API peruana externa.

## 3. Arquitectura de datos — entender esto antes de tocar nada

`KAPITAL_STORAGE_BACKEND=V2_COMPAT`: habla con el Supabase nuevo (`kapital-routing-v2`)
**conservando el contrato histórico**. Toda la aplicación vive en **una sola fila**:
`public.app_state` donde `id = 1`.

```
public.app_state (id=1)
├── usuarios (jsonb)          ~3,42 MB
│   ├── <112 usuarios reales>
│   │   └── _auth_sessions[]  ← las sesiones viven DENTRO de cada usuario
│   ├── __flota__             ~37 KB   (108 unidades, clave = padrón/unidad_id)
│   ├── __notifications__     ~28 KB
│   ├── __routes_summary__    ~16 KB
│   ├── __historial_rutas__   (vacío)
│   └── __lock__
└── rutas (jsonb)             ~526 KB
```

Snapshot completo: **~3,95 MB**.

**Tres trampas que ya causaron bugs reales:**

1. **`unidad_id` ≠ `real_placa`.** La clave de `__flota__` es el padrón, no la placa física.
   El path param de FastAPI se llama `placa` pero semánticamente es `unidad_id` — nombre
   heredado, no lo creas. Usar la placa física como clave fue la causa raíz del bug del PR #2.
2. **Estado en memoria que no persiste.** `usuarios_db`, `conductores_db`,
   `rutas_estado_actual`, `notifications_db` son globales de Python. En Vercel **no sobreviven
   un cold start**. De ahí `reload_db(force=True)` antes de escribir y la verificación por
   relectura. Es la causa de los reportes "los datos desaparecen".
3. **Escritura parcial = pérdida de datos.** Editar una unidad reconstruyendo el dict borra
   `base`, `marca`, `modelo`, `ano`, `color` y los `*_doc`. Siempre: leer → merge sobre
   allow-list explícito → persistir → **verificar releyendo**.

## 4. Egress de Supabase — problema recurrente, cuantificado

**Defensas que existen. No revertir ninguna.**
Caché backend TTL 45 s (`KAPITAL_DB_CACHE_TTL_SECONDS`, acotado 30–60) · single-flight por
event loop · circuit breaker (3 fallos → 15 s) con backoff · proyecciones PostgREST por clave
(`usuarios->__flota__` ≈ 37 KB en vez de 3,95 MB) · frontend con polling de 90 s, suspensión
por `document.hidden`, backoff 60 s → 10 min, cooldown de actividad 15 s y **suspensión total
del polling cuando el WebSocket está conectado**.

**Los tres agujeros abiertos:**

1. 🔴 **Autenticar cuesta 3,42 MB.** `get_user_by_session()` hace un **escaneo lineal sobre
   los 112 usuarios** buscando el hash del token, porque las sesiones se guardan dentro de
   `usuarios[*]._auth_sessions`. Validar *cualquier* sesión exige el blob entero de usuarios.
   Es el acoplamiento que encarece todo lo demás.

2. 🔴 **Las escrituras de flota fuerzan lectura completa antes de autenticar.** `POST`, `PUT`
   y `DELETE /api/flota/*` empiezan con `reload_db(force=True)`, que **salta el caché TTL y
   descarga los 3,95 MB**; `require_request_actor` corre *después*. **Una petición anónima
   cuesta ~4 MB de egress antes de ser rechazada con 401.** 100 peticiones = 400 MB. El orden
   no es arbitrario: validar la sesión necesita `usuarios_db` cargado (punto 1). Se arregla de
   verdad sacando las sesiones del blob.

3. 🟡 **40 llamadas a `reload_db` (estado completo) frente a ~15 usos de cargadores ligeros.**
   Las proyecciones existen pero se usan poco y solo en la ruta compat. Lo que salva hoy al
   sistema es el TTL de 45 s, no las proyecciones.

## 7. Hallazgos vivos, por severidad

### 🔴 A. El WebSocket permite suplantar a cualquier usuario
`/ws/{user_id}` toma el identificador del path y llama a `ws_manager.connect(user_id, ...)`
sin validar sesión. Quien abra un socket con el identificador de un admin recibe sus
broadcasts. Rompe dos invariantes del PR #1: *no identity spoofing* y *no privilege bleed*.

### 🔴 B. Datos de pasajeros accesibles sin sesión
`/api/cliente/rutas/{empresa_id}`, `/api/mis-rutas/{conductor_id}` y
`/api/conductor/notifications?email=` no piden nada. Conociendo o adivinando un `empresa_id`
se leen rutas y agentes de esa empresa, sobre 2.645 pasajeros reales. PII en producción.

### 🔴 C. `KAPITAL_AUTH_ENFORCED=true` sin manejo de 401 en el frontend
El PR #2 activó el flag cuyo apagado era condición explícita del DoD del PR #1. Con TTL de
sesión de 12 h, cuando a un admin le caduca la sesión el backend responde `401` y el frontend
no lo interpreta: no redirige al login, no avisa; los botones fallan con errores genéricos o
en silencio. **Depende de si Vercel Production define la variable explícitamente** — si allí
está en `false`, el default no aplica. **Verificarlo es el primer paso de todo.**

### ✅ D. Un usuario desactivado podía iniciar sesión — **cerrado en el Lote 1**
`deactivate_user` escribe `estado='Inactivo'` y el login solo bloqueaba `Pendiente`.
Ahora login y sesión comparten `account_block_reason()`.

### ✅ I. Conductores en revisión documental bloqueados de su propio portal — **cerrado en el Lote 1**
Destapado al implementar D. El campo `estado` mezcla **dos ejes**: ciclo de vida de la cuenta
(`Activo`/`Pendiente`/`Rechazado`/`Inactivo`) y avance documental del conductor
(`Pendiente Revisión`/`Documentos Observados`). `require_request_actor` rechazaba con 403 todo
lo que no fuera exactamente `"Activo"`, y `/api/user/profile` está gateado con él: **con
`AUTH_ENFORCED=true`, cualquier conductor en onboarding o con documentos observados recibía 403
en su propio perfil** — justo los que necesitan entrar para resubir. Sin manejo de 401/403 en el
frontend, lo veían como una pantalla rota.
Corregido con una lista explícita de estados de cuenta bloqueantes; los documentales no bloquean.
**Lección para el siguiente agente: no tratar `estado` como un único eje.**

### 🟡 E. CORS wildcard con credenciales
`allow_origins=["*"]` + `allow_credentials=True` hace que Starlette refleje cualquier origen.
Atenuante real: la cookie se emite con `samesite="lax"`, así que una petición cross-site no la
lleva. Es fallo de defensa en profundidad y violación de la especificación, **no un robo de
sesión explotable hoy**. No exagerarlo al reportarlo.

### 🟡 F. Egress: lectura completa antes de autenticar
Ver §4.2. ~4 MB por petición anónima rechazada.

### 🟡 G. Documentación que contradice al código
`docs/phase-1/README.md` dice `false` donde el código dice `true`. `CLAUDE.md` afirma ~2.180
líneas en `api/index.py`; son ~4.620. `CLAUDE.md` §10 exige corregirlo donde se detecte.

### 🟢 H. Token hardcodeado
`JSON_PE_TOKEN` tiene un literal como fallback en `api/index.py`, commiteado. Rotar y retirar.

## 8. Plan de trabajo — ordenado por dependencias reales

Cada lote: pequeño, reversible, con pruebas, y pasando el trinquete de calidad. Un lote por
PR. No empezar el siguiente sin cerrar el anterior.

### Lote 0 — Contención *(antes que nada, requiere autorización del usuario)*
Verificar el valor de `KAPITAL_AUTH_ENFORCED` en Vercel Production. Si está en `true` sin
manejo de 401, decidir con el usuario si se pone en `false` hasta cerrar los lotes 1–2. Es un
flag: reversible y sin desplegar código.

### ✅ Lote 1 — Identidad de sesión completa — **hecho** (commit siguiente a `da0339d`)
`GET /api/auth/me` · `POST /api/auth/logout` (revoca la sesión en servidor, no solo borra la
cookie) · login bloquea `Inactivo` y `Rechazado` además de `Pendiente` (hallazgo D).
Sin estas piezas el frontend no puede saber quién es ni reaccionar a un 401 — por eso el
PR #1 las pone en P0.

### ✅ Lote 2 — Cliente HTTP centralizado y manejo de 401 — **hecho (parcial por diseño)**
`src/utils/apiClient.js` con manejador global de 401. **Se migraron solo las ~11 llamadas cuyos
endpoints están gateados**; las demás no pueden devolver 401 todavía, y migrarlas a ciegas sin
poder validar en navegador era riesgo sin beneficio. La migración sigue al gateo: cada endpoint
que cierre el Lote 3, migra su llamada.

Decisiones que conviene no deshacer:
- **Un 401 cierra sesión; un 403 no.** Un 403 puede ser solo un rol sin permiso, y expulsar al
  usuario por eso sería peor que mostrarle el motivo.
- `logoutSession()` nunca lanza: si el backend no contesta, el estado local se limpia igual.
- La rehidratación pide `/api/auth/me` y, si el perfil falla después, **no expulsa**: la sesión
  es válida aunque el perfil no cargue.
- `verify:baseline` ahora incluye `test:frontend`. **Las pruebas de frontend no se ejecutaban en
  CI**: `test:flota-status` nunca estuvo en la cadena.

### Lote 3 — Cerrar el acceso cruzado *(P0, cierra los hallazgos B y D)*
Ownership en `/api/mis-rutas/{conductor_id}`, `/api/cliente/rutas/{empresa_id}` y
`/api/conductor/notifications`. Restringir `POST /api/notifications`. IDs de notificación sin
colisión.

### Lote 4 — WebSocket autenticado *(P0, cierra el hallazgo A)*
El handshake valida la cookie de sesión; el `user_id` lo determina el servidor a partir de la
sesión, nunca el path.

### Lote 5 — CORS explícito *(P1, cierra E)*
Lista de orígenes permitidos; prohibido wildcard con credenciales.

### Lote 6 — Matriz de permisos *(P0/P1)*
Sustituir `_ADMIN_ROLES` por una matriz recurso × acción. Hacerlo **después** de que el
gateo esté completo: primero cubrir, luego centralizar.

### Lote 7 — OCC en `app_state` *(P1)*
Evitar pérdidas silenciosas de actualizaciones entre instancias serverless concurrentes.

### Decisión registrada — separar backend y frontend en dos repositorios: **NO, por ahora**

Evaluado el 2026-09-15 a petición del usuario y descartado. No es preferencia monorepo: el
mismo origen es hoy **carga estructural**.

- La cookie es `HttpOnly` + `SameSite=Lax` + `path=/`. Con dos dominios habría que pasarla a
  `SameSite=None; Secure`, perdiendo la protección CSRF que hoy es gratuita — y **despertando
  el hallazgo E**, que solo está dormido porque `Lax` lo neutraliza.
- Se pierde el **despliegue atómico** justo en los lotes 1–4, que cambian el contrato de auth.
  Un frontend desplegado antes que su backend rompe el login a 112 usuarios reales.
- El baseline se fragmenta: `verify:baseline` corre las 82 pruebas de Python y el build de Vite
  en un solo comando, y el trinquete de calidad mide contra números únicos.
- **41 de las 42 llamadas son relativas** (`/api/...`) y el WebSocket se construye desde el
  protocolo de la página. Dividir hoy = tocar todos los puntos de llamada.

**Precondiciones para reconsiderarlo:** lotes 1–6 cerrados · CORS explícito con lista de
orígenes · Lote 2 hecho (cliente HTTP centralizado, que deja un único punto donde definir la
base URL). Con eso, dividir baja de "riesgo de seguridad + skew de versiones + refactor de 42
sitios" a un cambio de configuración.

Lo que probablemente motivaba la pregunta —un backend de ~4.625 líneas viviendo en
`frontend/api/index.py`— se resuelve mejor con el Lote P2 (modularización interna, riesgo de
despliegue cero) que con una división de repos. Mover la carpeta fuera de `frontend/` cambia
la raíz del proyecto en Vercel: toca producción, requiere autorización y un momento tranquilo.

### Fase 2 — Normalización *(requiere autorización explícita)*
Separar `app_state` en tablas. **Empezar por sacar las sesiones a su propia tabla**: ataca a
la vez los hallazgos §4.1 y §4.2, y es el cambio con mejor relación impacto/riesgo pendiente.
Andamiaje en `scripts/migration/` y `supabase/migrations/`. El SQL de compat lo dice: la tabla
puente *"must never write or delete normalized data"*. **No mezclar Fase 2 dentro de un fix de
Fase 1.**

## 10. Reglas innegociables

- Trabajar **solo en `develop`**. Nunca `push --force`, `reset --hard`, `checkout -- .`,
  `clean -fd`. Nunca descartar cambios locales ni archivos sin seguimiento.
- **Nunca** merge a `main`, deploy, redeploy, cambio de variables en Vercel Production,
  promoción de previews ni borrado de deployments **sin autorización explícita y actual**.
- **Nunca activar un flag antes que su precondición documentada.** Es el error que produjo el
  hallazgo C.
- `git add` **siempre explícito por archivo**. Nunca `git add .` ni `-A`.
- Nunca mostrar, pegar ni loguear el contenido de `frontend/.env`. La clave secreta de
  Supabase va solo en backend y solo en el header `apikey` — nunca `Authorization: Bearer`,
  nunca con prefijo `VITE_`/`NEXT_PUBLIC_`.
- **UI:** nunca colores hardcodeados (usar tokens `var(--kapital-*)`), nunca emojis nativos
  (usar `lucide-react`). El trinquete de calidad lo verifica.
- **Estados de vencimiento:** la fecha es la única fuente de verdad. Nunca persistir textos
  derivados ("Vigente", "Vencido", "N/A"). Usar siempre `getDocumentStatus()` de
  `src/utils/flotaDocumentStatus.js`. Umbral de 15 días inclusive; hoy = "Por vencer".
- Antes de cualquier prueba que escriba datos reales: identificar exactamente qué se modifica,
  respaldar, usar una unidad temporal, verificar persistencia releyendo, **revertir**,
  confirmar conteos finales.
- Las pruebas de baseline **nunca tocan Supabase real** (requisito del PR #1). Mockear.
- **Validación obligatoria** desde `frontend/`:
  `npm run test:flota-status`, `npm run build`, `npm run test:baseline`,
  `npm run quality:baseline`, `venv\Scripts\python.exe -m py_compile api\index.py`,
  `git diff --check`.
  En Windows, si npm no encuentra python:
  `$env:PATH=(Resolve-Path '.\venv\Scripts').Path+';'+$env:PATH`
- Los scripts sueltos en `frontend/` (`check_*.py`, `clear_*.py`, `sync_flota*.py`…) son
  herramientas puntuales de debugging contra Supabase. **No son código productivo y no se
  limpian sin confirmar.** `kapital.db` está vacío, es un vestigio.
